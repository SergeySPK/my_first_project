Ответы на вопросы по практической работе 17

1. В чём разница между управляемыми и неуправляемыми компонентами в формах React?
Управляемые компоненты - компоненты, в которых значения полей формы хранятся в состоянии React (useState). Каждое изменение поля вызывает обработчик onChange, который обновляет state, и новое значение передаётся обратно в поле через атрибут value. React полностью контролирует значение поля на каждом этапе.
Неуправляемые компоненты - компоненты, в которых значения полей хранятся непосредственно в DOM. Доступ к значениям получается через useRef в нужный момент (обычно при отправке формы). React не отслеживает каждое изменение поля.

Основные различия:
- Источник истины: в управляемых - это state React, в неуправляемых - сам DOM.
- Контроль: управляемые дают полный контроль над значением поля (можно форматировать, валидировать в реальном времени), неуправляемые предоставляют значение только по запросу.
- Производительность: неуправляемые компоненты требуют меньше перерисовок, так как не вызывают setState при каждом вводе символа.
- Валидация: в управляемых валидацию легко делать в реальном времени, в неуправляемых - обычно при submit или blur.
- Сброс формы: в управляемых сброс делается через setState, в неуправляемых - через formRef.current.reset().

2. Когда следует использовать управляемые компоненты, а когда - неуправляемые?
Управляемые компоненты предпочтительнее в большинстве случаев, особенно когда:
- Нужна валидация в реальном времени (проверка email при вводе, совпадение паролей).
- Требуется динамическое изменение значения поля (автоформатирование телефона, маски ввода).
- Значение одного поля зависит от другого (например, поле "Город" меняется в зависимости от выбранной "Страны").
- Нужно условно блокировать кнопку отправки до заполнения всех обязательных полей.
- Требуется мгновенная обратная связь для пользователя (счётчик символов, индикатор силы пароля).

Неуправляемые компоненты уместны, когда:
- Форма простая и не требует сложной валидации (например, форма поиска).
- Нужна интеграция со сторонними библиотеками, которые сами управляют DOM.
- Важна производительность при большом количестве полей или частом вводе (например, поле поиска с debounce).
- Нужен быстрый прототип без сложной логики.
- Работа с файловыми полями (input type="file"), которые всегда неуправляемые, так как их value доступно только для чтения.

3. Какие методы используются для обработки событий в формах React?
Основные события форм в React:
- onChange - срабатывает при каждом изменении значения поля. Используется в управляемых компонентах для обновления state.
- onSubmit - срабатывает при отправке формы (клик по кнопке type="submit" или нажатие Enter). Обрабатывается на теге form.
- onBlur - срабатывает при потере фокуса полем. Часто используется для валидации после того, как пользователь закончил ввод.
- onFocus - срабатывает при получении фокуса. Полезно для показа подсказок или очистки ошибок.
- onInput - срабатывает при вводе, аналогично onChange, но работает на уровне DOM.
- onKeyDown, onKeyUp, onKeyPress - события клавиатуры, полезны для обработки специальных клавиш (Enter для отправки, Escape для отмены).

4. Как обрабатывать несколько полей ввода с одним обработчиком?
Для обработки нескольких полей одним обработчиком используется атрибут name у каждого поля и свойство e.target.name в обработчике. Это позволяет динамически обновлять нужное поле в state.

Пример с единым объектом formData:
const [formData, setFormData] = useState({ name: '', email: '', age: '' });

const handleChange = (e) => {
  const { name, value, type, checked } = e.target;
  setFormData(prev => ({
    ...prev,
    [name]: type === 'checkbox' ? checked : value
  }));
};

В JSX каждому полю задаётся name, совпадающий с ключом в state:
<input name="name" value={formData.name} onChange={handleChange} />
<input name="email" value={formData.email} onChange={handleChange} />

Для checkbox используется проверка type === 'checkbox' ? checked : value, так как у чекбоксов значение берётся из checked, а не из value.

Для radio-кнопок все кнопки группы имеют одинаковый name, и в state хранится выбранное значение.

Такой подход уменьшает количество кода и упрощает добавление новых полей - достаточно добавить ключ в state и поле с соответствующим name.

5. Какие подходы к валидации форм в React вы знаете?
Существует несколько подходов к валидации:
   1) Валидация при отправке (onSubmit): проверка всех полей происходит только при нажатии кнопки отправки. Простой подход, но пользователь видит ошибки только после попытки отправить форму.
   2) Валидация при потере фокуса (onBlur): поле проверяется, когда пользователь уходит с него. Баланс между навязчивостью и своевременностью - ошибка показывается после завершения ввода, но до отправки.
   3) Валидация в реальном времени (onChange): поле проверяется при каждом изменении. Даёт мгновенную обратную связь, но может быть навязчивым (ошибка появляется, пока пользователь ещё печатает).
   4) Комбинированный подход (с флагом touched): валидация начинается после первого blur на поле, затем продолжается в реальном времени. Это оптимальный подход - пользователь не видит ошибку во время первого ввода, но получает мгновенную обратную связь при исправлении.
   5) Использование HTML5-валидации: атрибуты required, pattern, minLength, type="email" и другие. Браузер сам проверяет поля и показывает сообщения. Можно комбинировать с кастомной валидацией через setCustomValidity().
   6) Сторонние библиотеки: Formik, React Hook Form, Yup, Zod. Предоставляют готовую инфраструктуру для валидации, управления состоянием формы и обработки ошибок.

6. Как предотвратить стандартное поведение формы (перезагрузку страницы)?
Стандартное поведение формы при отправке - это перезагрузка страницы и отправка данных на сервер. В React-приложениях (SPA) это нежелательно, так как приводит к потере состояния.
Для предотвращения используется метод e.preventDefault() в обработчике onSubmit:

const handleSubmit = (e) => {
  e.preventDefault();
  // Дальнейшая обработка данных формы
};

e.preventDefault() отменяет стандартное действие браузера. После этого форма не перезагружает страницу, и можно обработать данные самостоятельно - провести валидацию, отправить через fetch/axios, обновить state.
Альтернативный способ - использовать кнопку type="button" вместо type="submit", тогда форма не будет отправляться по нажатию Enter. Но этот подход менее семантичен.
Также можно добавить атрибут noValidate к форме, чтобы отключить встроенную браузерную валидацию и полностью контролировать процесс через JavaScript.

7. Что такое "поднятие состояния" (lifting state up) в контексте форм?
Поднятие состояния - паттерн, при котором состояние перемещается из дочернего компонента в ближайшего общего родителя, чтобы несколько компонентов могли использовать и изменять одни и те же данные.
В контексте форм это необходимо, когда:
- Данные формы используются в нескольких компонентах (например, форма ввода и компонент отображения результатов).
- Родительскому компоненту нужно знать о изменениях в форме (например, для блокировки кнопки отправки на уровне приложения).
- Несколько форм должны быть синхронизированы между собой.

Пример: если есть компонент формы UserForm и компонент UserList, который отображает добавленных пользователей, состояние списка пользователей должно храниться в общем родителе App. UserForm получает через props функцию addUser, которая обновляет state в App, а App передаёт обновлённый список в UserList.
Таким образом создаётся единый источник истины (single source of truth) - данные хранятся в одном месте, а компоненты только читают их через props и сообщают об изменениях через callback-функции.
Поднятие состояния также применяется при валидации: если ошибка в одном поле влияет на доступность другого поля (например, кнопка отправки блокируется, пока все поля не заполнены), состояние валидации поднимается на уровень формы или выше.
