Ответы на вопросы по практической работе 16

1. В чём разница между useState и useReducer? Когда использовать каждый?
useState - простой хук для хранения одного значения или небольшого объекта.
Когда использовать useState:
- Состояние простое - одно значение или объект с несколькими полями.
- Логика обновления тривиальная - например, просто увеличить счётчик на единицу.
- Пример из моей работы: Counter, UserForm, TodoList - там достаточно useState, потому что логика простая и понятная.

useReducer - хук для управления сложным состоянием через reducer-функцию, которая принимает текущее состояние и действие (action) и возвращает новое состояние. Это похоже на мини-версию Redux внутри компонента.
Когда использовать useReducer:
- Состояние сложное - много связанных полей, которые меняются вместе.
- Логика обновления запутанная - много ветвлений и условий.
- Следующее состояние зависит от предыдущего сложным образом.

Преимущества useReducer:
- Логика обновления вынесена в одно место - reducer-функцию, её легче читать и тестировать.
- Reducer - чистая функция, её можно протестировать отдельно от компонента.
- Удобно отлаживать - видны все action.type, понятно, что произошло.

2. Как работает массив зависимостей в useEffect? Что произойдёт если его не указать?
Массив зависимостей указывает React, при изменении каких значений нужно перезапускать эффект. React сравнивает значения из массива между рендерами - если хоть одно изменилось, эффект выполняется снова.

Если указать массив []:
- useEffect с пустым массивом [] - эффект выполнится только один раз, при первом рендере (монтировании). Это аналог componentDidMount в классовых компонентах.
- useEffect с зависимостями [count] - эффект выполнится при монтировании и при каждом изменении count.

Если не указать массив зависимостей:
- Эффект будет запускаться после каждого рендера, что часто приводит к бесконечным циклам, особенно если внутри есть setState.

3. Что такое "stale closure" в хуках и как использовать функциональные обновления чтобы избежать этой проблемы?
"Stale closure" (устаревшее замыкание) - ситуация, когда функция "помнит" старое значение переменной, хотя она уже изменилась. Это происходит потому, что замыкание захватывает переменную на момент создания функции, а не на момент её вызова.

Пример проблемы: если в таймере использовать setCount(count + 1) внутри setInterval с пустым массивом зависимостей, то count всегда будет равен 0 - начальное значение, потому что замыкание "запомнило" именно его. Таймер будет работать, но счётчик не будет расти.

Решение - функциональное обновление:
- Вместо setCount(count + 1) писать setCount(prev => prev + 1).
- Функция получает актуальное предыдущее значение как аргумент, поэтому stale closure не возникает.

Другие способы избежать stale closure:
- Добавить переменную в массив зависимостей useEffect.
- Использовать useRef для хранения актуального значения - оно не вызывает rerender, но всегда доступно.
- Использовать функциональные обновления setState(prev => ...).

4. Когда действительно нужны useCallback и useMemo? Не являются ли они преждевременной оптимизацией?
useMemo кэширует результат вычислений - пересчитывает только при изменении зависимостей.
useCallback кэширует саму функцию - пересоздаёт только при изменении зависимостей.

Когда действительно нужны:
- useMemo: тяжёлые вычисления.
- useCallback: когда функция передаётся как props дочернему компоненту, обёрнутому в React.memo. Иначе дочерний компонент будет перерисовываться при каждом рендере родителя, потому что функция каждый раз новая.
- useCallback: когда функция используется в зависимостях другого useEffect.

Когда это преждевременная оптимизация:
- Простые вычисления - сложение, конкатенация строк. Кэширование дороже, чем сам пересчёт.
- Когда компонент не передаёт функции в дочерние компоненты.
- Когда нет проблем с производительностью - нужно сначала измерить через React DevTools Profiler, а потом оптимизировать.

5. Как useRef отличается от useState? В каких сценариях useRef незаменим?
Главное отличие: изменение ref.current не вызывает перерисовку компонента. Изменение state - вызывает.

Сравнение:
- useState: вызывает rerender при изменении, значение сохраняется между рендерами, асинхронное обновление, для UI-данных.
- useRef: не вызывает rerender при изменении, значение сохраняется между рендерами, синхронное обновление, для служебных данных.

Сценарии, где useRef незаменим:
1) Доступ к DOM-элементам - в моей работе FocusInput использует inputRef.current.focus() для программного фокуса на поле ввода.
2) Хранение предыдущих значений - в моей работе PreviousValue хранит предыдущее значение в previousValue.current, обновляя его в useEffect.
3) Хранение таймеров и интервалов - чтобы можно было их очистить в cleanup-функции useEffect.
4) Хранение флагов - например, isMounted для предотвращения обновления состояния после unmount компонента.
5) Хранение мутирующих данных - когда нужно менять значение, но не вызывать rerender

6. Какие правила хуков существуют и почему их нельзя нарушать?
Правила хуков:
- Вызывать хуки только на верхнем уровне - не внутри условий, циклов, вложенных функций.
- Вызывать хуки только из React-функций - функциональных компонентов или кастомных хуков.

Почему нельзя нарушать:
React использует связанный список для хранения состояния хуков. При каждом рендере React обходит хуки в том же порядке, что и в предыдущем рендере. Если порядок изменится - например, из-за условия - React не сможет сопоставить хуки с их состоянием. Это приведёт к багам и ошибкам.

Пример нарушения: если написать useState внутри if (condition), то при изменении condition порядок хуков изменится, и React сломается - он не поймёт, какой useState какому состоянию соответствует.

Как правильно: всегда объявлять хуки на верхнем уровне компонента, а условия и циклы использовать уже после объявления хуков - для работы с их значениями.

Для обеспечения правил существует ESLint-плагин eslint-plugin-react-hooks, который автоматически проверяет код и предупреждает о нарушениях.

7. Как создать кастомный хук и какие лучшие практики следует соблюдать?
Кастомный хук - обычная JavaScript-функция, которая:
- Начинается с "use" (например, useLocalStorage, useFetch).
- Внутри вызывает другие хуки (useState, useEffect и т.д.).

Лучшие практики:
- Имя с "use" - чтобы ESLint понимал, что это хук, и применял правила хуков.
- Изоляция логики - хук должен решать одну задачу (Single Responsibility).
- Возвращать понятный API - массив [value, setValue] или объект { data, loading, error }.
- Обрабатывать ошибки (try/catch) - особенно в асинхронных операциях.
- Очистка в cleanup - если хук использует setInterval, addEventListener и т.д., нужно очищать в return () => {...}.
- Ленивая инициализация - если начальное значение требует вычислений, использовать функцию: useState(() => expensiveCalc()).
- Не злоупотреблять - если логика используется только в одном компоненте, не нужно выносить в хук.

8. В чем преимущества использования useContext перед передачей props через несколько компонентов?
Проблема "prop drilling" - когда нужно передать данные через много уровней компонентов, которые сами эти данные не используют.

Пример без Context: App (theme) -> Layout (theme) -> Header (theme) -> ThemeToggle (theme). Каждый промежуточный компонент должен принимать и передавать theme в props, хотя ему это не нужно.
Решение с Context: ThemeProvider (theme) -> App -> Layout -> Header -> ThemeToggle (useContext). ThemeToggle получает theme напрямую из Context, минуя промежуточные компоненты.

Преимущества useContext:
- Избавление от prop drilling - данные доступны любому компоненту в дереве.
- Чище код - промежуточные компоненты не загромождены лишними props.
- Легче рефакторить - не нужно менять сигнатуры компонентов при добавлении новых данных.
- Глобальное состояние - для темы, локализации, данных авторизованного пользователя.

Недостатки useContext:
- Перерендер всех потребителей - при изменении Context все компоненты, использующие его, перерисовываются.
- Сложнее тестировать - нужно оборачивать в Provider.
- Не для всего - если данные нужны только в 1-2 компонентах, лучше обычные props.

9. Как обрабатывать асинхронные операции в кастомных хуках?
Основные подходы:
1) async/await внутри useEffect:
   - Объявить async-функцию внутри useEffect и сразу её вызывать.
   - Использовать try/catch для обработки ошибок.
   - Устанавливать состояния loading, error, data для полного контроля.

2) Флаг isMounted для предотвращения обновления после unmount:
   - Создать переменную isMounted = true в начале useEffect.
   - В cleanup-функции установить isMounted = false.
   - Перед setState проверить isMounted - если компонент уже размонтирован, не обновлять состояние.

3) AbortController для отмены запросов:
   - Создать AbortController в useEffect.
   - Передавать controller.signal в fetch.
   - В cleanup вызывать controller.abort() - это отменит запрос, если компонент размонтировался.

10. Какие способы отладки хуков вы знаете?
1) React Developer Tools (расширение браузера):
   - Вкладка "Components" - показывает все хуки компонента и их текущие значения.
   - Можно видеть состояние useState, зависимости useEffect, значения useRef.
   - Самый мощный инструмент для отладки хуков.

2) Console.log:
   - Простой, но эффективный способ.
   - Логирование в useEffect помогает понять, когда эффект выполняется.

3) ESLint плагин eslint-plugin-react-hooks:
   - Автоматически проверяет правила хуков.
   - Предупреждает о пропущенных зависимостях в useEffect.
   - Настраивается в package.json

4) Кастомные хуки для отладки:
   - Можно создать хук useWhyDidYouUpdate, который логирует, какие props изменились между рендерами.
   - Полезно для поиска причин лишних перерендеров.

5) React DevTools Profiler:
   - Записывает рендеры и показывает, какие компоненты перерисовываются.
   - Помогает найти проблемы с useMemo/useCallback - если компонент ререндерится без причины, значит оптимизация не работает.

6) Отладка в IDE:
   - Точки останова в коде хуков.
   - Пошаговое выполнение (step over/into).
   - Просмотр значений переменных в реальном времени.
